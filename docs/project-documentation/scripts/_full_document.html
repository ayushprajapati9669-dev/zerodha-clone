Chapter 1 — Project Overview

1.1 Executive Summary

Zerodha Clone is a production-grade, full-stack stock trading, portfolio management, and simulated investment platform modeled after India's premier discount broker, Zerodha (Kite). The system implements a full-featured financial trading engine supporting equity delivery (CNC — Cash 'N Carry) and intraday margin trading (MIS — Margin Intraday Square-off), market orders, limit orders with price triggers, cash and stock reservation locking, real-time market data streaming via WebSockets, competitive paper-trading tournaments, portfolio analytics, risk guard management, trading journals, strategy backtesting, and an integrated generative AI financial assistant powered by Google Gemini.

1.2 Core Project Goals

  • Institutional-Grade Trading Mechanics: Replicate real stock market order execution mechanics, including available vs. used vs. reserved balances, limit order price condition triggers, and atomic inventory allocations.
  • Resilient Dual-Mode Execution: Seamless operation with live external APIs (TrueData market feed, Twilio SMS OTP, MongoDB, Google Gemini) while maintaining offline and development fallbacks so the system remains interactive under all runtime environments.
  • Real-Time Data Distribution: Event-driven WebSocket architecture utilizing Socket.IO for pushing real-time order status updates, price alert triggers, fund notifications, and tournament leaderboard rankings.
  • Gamified Simulated Learning: Isolated tournament and paper-trading environments enabling risk-free trading competitions with independent virtual capital, real-time leaderboards, and automated prize/winner settlement.
  • Context-Aware Portfolio Intelligence: Server-side AI assistant that dynamically queries user holdings, active positions, recent orders, and available funds to formulate personalized financial and risk commentary.

Chapter 2 — Complete System Architecture

2.1 Overall System Architecture

The system utilizes a modern, unified full-stack architecture that cleanly separates client presentation from backend domain logic while enabling seamless single-origin execution without cross-origin resource sharing (CORS) friction.

Architectural Components Walkthrough:

  1. Browser Client Layer: The presentation tier is built with React 19 and Vite. In the original repository, two distinct Vite apps existed: frontend/ (marketing, landing pages, education) and dashboard/ (Kite trading terminal). In AI Studio and production deployment, these are unified under a single origin on port 3000, eliminating browser cross-port redirects.
  2. Unified Express Gateway & Vite Middleware: The Node.js 22 runtime server boots an Express 5 instance on port 3000. In development mode, Vite's internal development server is mounted as an Express middleware (vite.middlewares), handling HMR and JSX on-the-fly. In production, pre-compiled static assets in dist/ are served directly with an SPA catch-all route.
  3. Middleware Pipeline: Incoming HTTP requests pass through security and parsing middlewares:
    • cors({ origin: true, credentials: true }): Permits secure credentialed requests.
    • cookieParser(): Extracts the token cookie containing the signed JSON Web Token.
    • isLoggedInMiddleware.js: Decodes JWT, validates session active status, and checks tokenVersion to support global logout.
    • orderValidation.js / validateUser.js: Joi schema validation catching invalid inputs before controllers execute.
  4. Domain Services & State Machines: Business logic is isolated from HTTP handlers into dedicated services (createOrderServices.js, tournamentService.js, aiService.js, trueDataService.js).
  5. Persistence Layer: MongoDB stores structured documents across 15 schemas. When executing orders or balance modifications, Mongoose leverages native multi-document transactions with atomic session rollbacks.
  6. Real-Time Event Multiplexer (Socket.IO): Attached to the native HTTP server instance, Socket.IO routes events into isolated rooms (user:{userId} and tournament:{id}).

2.2 HTTP Request Lifecycle

When a user initiates an action in the UI (for example, clicking "Buy 10 Reliance CNC at ₹2,525"):

  1. HTTP Transmission: The Axios client transmits a POST /api/orders request with { withCredentials: true }, automatically attaching the browser's HTTP-only cookie.
  2. Middleware Verification: Express matches the route. isLoggedIn extracts the cookie, runs jwt.verify(token, JWT_SECRET), queries the user model to verify tokenVersion, and attaches req.user = { userId, role, status }.
  3. Payload Validation: The Joi validation middleware parses req.body against orderValidationSchema.js. If validation fails (e.g., negative quantity or missing symbol), a 400 Bad Request is returned immediately without touching the database.
  4. Controller Execution: orderController.js invokes createOrderServices.js, passing the sanitized payload and authenticated userId.
  5. Transactional Execution: A MongoDB transaction session begins:
    • Calculates required capital: qty * price.
    • Checks availableBalance >= requiredAmount.
    • Updates user ledger: availableBalance -= requiredAmount, usedBalance += requiredAmount.
    • Creates/updates Holding or Position record.
    • Inserts Order record with status completed.
  6. Event Dispatch & Response: Upon successful commit, a notification is written, Socket.IO emits new-notification to user:{userId}, and HTTP 201 Created is returned to the client. The frontend AppContext receives the response and triggers state re-fetching.

2.3 Real-Time WebSocket & Socket.IO Flow

The real-time infrastructure provides sub-second push updates for:

  • Order Execution Notifications: When limit orders trigger in the background via live market ticks, user alerts fire without polling.
  • Price Alerts: Triggered when a stock reaches a user-defined price ceiling or floor.
  • Tournament Leaderboards: Real-time rank and ROI calculations broadcast to all active competitors inside tournament:{id}.

Chapter 5 — Authentication, OTP & Security Architecture

5.1 Authentication Architecture Overview

Authentication is architected as a hybrid password and phone-based OTP system designed to mirror the multi-factor security expectations of modern Indian financial brokerages. The system uses signed JSON Web Tokens (JWT) transmitted via secure, HTTP-only cookies, paired with an active database-backed tokenVersion check that supports instant global session invalidation.

5.2 Mobile OTP Verification Challenge Flow

To prevent phone number spoofing and unauthorized account creation, mobile onboarding uses a multi-step challenge verification flow:

  1. Challenge Creation (POST /api/auth/otp/send):
    • User submits a 10-digit mobile number.
    • System validates number using regex /^\d{10}$/.
    • Rate-limiting check: Queries OtpChallengeModel to ensure no more than 3 challenges were requested in the last 5 minutes. If exceeded, returns HTTP 429.
    • Existing unconsumed challenges for this number are invalidated (isConsumed: true).
    • Dispatches verification SMS via Twilio Verify. If Twilio credentials are not configured, the system logs a mock challenge code (123456) to ensure uninterrupted development and testing.
  2. Challenge Verification (POST /api/auth/register/verify-mobile):
    • User submits the 6-digit OTP code received on SMS.
    • Twilio Verify checks code validity (or verifies against test mock code 123456).
    • Upon approval, the challenge is marked isConsumed: true.
    • A short-lived signed JWT verification token is generated: jwt.sign({ mobile, verified: true, challengeId }, JWT_SECRET, { expiresIn: '15m' }).
    • This token must be included in the subsequent registration payload to prove phone ownership.

5.3 User Registration & Client ID Generation

Once verified, the user submits registration details (POST /api/auth/register):

  • Validates name, unique email, verified mobile, password (minimum 6 characters), and verificationToken.
  • Decodes the verification token, confirms that decoded.mobile === req.body.mobile and decoded.verified === true.
  • Validates that the challenge record has not already been used for registration (challenge.usedForRegistration === false), then marks it used.
  • Generates a unique Zerodha 6-character Client ID (e.g., ZR9669) using random alphanumeric character generation and collision detection.
  • Hashes the password with bcryptjs using 10 salt rounds.
  • Initializes a default Funds document for the new user with ₹1,00,000 initial virtual capital.
  • Initializes a default WatchlistList titled "Watchlist 1" populated with blue-chip Indian equities (Reliance, TCS, Infosys, HDFC Bank, ICICI Bank, SBI, ITC, Bharti Airtel).
  • Signs the session JWT and sets the HTTP-only cookie, automatically logging the user into their account.

5.4 Token Versioning & Global Session Revocation

A frequent security flaw in stateless JWT architectures is the inability to revoke tokens before their expiration window elapses. Zerodha Clone solves this using Token Versioning: 

// JWT Payload structure:
{
  "userId": "68c123456789abcdef123455",
  "role": "trader",
  "tokenVersion": 3,
  "iat": 1791780813,
  "exp": 1792385613
}

When a user invokes POST /api/auth/logout-other-sessions or changes their password:

  1. The backend executes User.findByIdAndUpdate(userId, { $inc: { tokenVersion: 1 } }).
  2. The current active user is re-issued a fresh cookie with the incremented version.
  3. Every subsequent request from any other device or browser containing the older tokenVersion fails the check in isLoggedInMiddleware.js: 
    if (user.tokenVersion !== decoded.tokenVersion) {
  return res.status(401).json({
    success: false,
    message: "Session expired. Please login again."
  });
}
  4. All previous sessions are immediately invalidated across all devices without requiring a centralized token blacklist.

5.5 Cookie Security Specifications

Cookie Attribute Configuration Security Protection Provided
httpOnly true Prevents client-side JavaScript from accessing document.cookie, completely mitigating Cross-Site Scripting (XSS) token theft.
sameSite 'lax' Protects against Cross-Site Request Forgery (CSRF) by preventing third-party origins from sending the authentication cookie during cross-site requests.
maxAge 24 * 60 * 60 * 1000 (1 day) Enforces session lifecycle boundaries, ensuring stale sessions expire naturally.
secure Conditional (false in dev, true in HTTPS prod) Ensures authentication cookies are transmitted exclusively over encrypted TLS connections in production.

Chapter 7 — Trading Engine & Order Execution

7.1 Trading Engine Architecture Overview

The core of the platform is an institutional paper-trading engine that faithfully replicates the financial rules, balance management, and lifecycle state transitions of real-world stock exchanges. It enforces atomic transaction safety, prevents overdrafts, implements cash and inventory reservations, and matches limit orders in real time against live market ticks.

7.2 Market Order Execution (Immediate Fill)

When a trader submits a Market Order:

  1. Price Resolution: The engine resolves the latest market price (LTP) from the in-memory cache populated by TrueData feeds.
  2. Pre-Trade Validation:
    • BUY Market: The total required capital is calculated: tradeAmount = qty * LTP. The system queries Funds inside an atomic MongoDB session. If availableBalance < tradeAmount, the transaction aborts with an Insufficient Funds error.
    • SELL Market (CNC): The system queries Holding for the user and symbol. If holding.quantity < qty, the transaction aborts with an Insufficient Quantity error. Short selling is prohibited in CNC delivery.
  3. Atomic Ledger & Inventory Mutation: Inside a MongoDB transaction session:
    • BUY CNC: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: -tradeAmount, usedBalance: tradeAmount }
});
Holding.findOneAndUpdate({ userId, symbol }, {
  $inc: { quantity: qty },
  $set: { averagePrice: newWeightedAverage, currentPrice: LTP }
}, { upsert: true });
    • SELL CNC: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: +tradeAmount, usedBalance: -originalCostBasis }
});
Holding.updateOne({ userId, symbol }, {
  $inc: { quantity: -qty }
});
      If the remaining holding quantity reaches 0, the holding document is removed.
  4. Order Insertion: An order document is created with status: 'completed', orderType: 'MARKET', and reservationReleased: true.

7.3 Limit Order Lifecycle & Reservation Engine

A Limit Order allows a trader to specify an exact maximum price they are willing to pay (Limit Buy) or minimum price they are willing to accept (Limit Sell). Because execution may occur minutes or hours later, the engine locks capital or inventory to guarantee settlement when the market condition triggers.

Step-by-Step Limit Order Lifecycle:

  1. Placement & Reservation (createOrderServices.js):
    • Limit BUY: The maximum required cash is calculated: reservedAmount = qty * limitPrice. This amount is moved immediately from availableBalance to reservedBalance: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: -reservedAmount, reservedBalance: +reservedAmount }
});
      The order is recorded with status: 'pending', reservedAmount, and reservationReleased: false.
    • Limit SELL: The share quantity is reserved from the holding: 
      Holding.updateOne({ userId, symbol }, {
  $inc: { quantity: -qty, reservedQuantity: +qty }
});
  2. Background Tick Evaluation (checkPendingLimitOrders.js): Whenever TrueData streams a price update (e.g., RELIANCE LTP = ₹2,480):
    • The worker queries for active pending orders for that symbol: Order.find({ symbol, status: 'pending' }).
    • Condition Check:
      • BUY Limit: Triggers if currentLTP <= order.price.
      • SELL Limit: Triggers if currentLTP >= order.price.
    • Two-Phase Execution Lock: To prevent race conditions from concurrent ticks, the worker uses an atomic lock: 
      const lockedOrder = await Order.findOneAndUpdate(
  { _id: order._id, status: 'pending' },
  { $set: { status: 'processing' } },
  { new: true }
);
      If another thread already acquired the lock, lockedOrder is null and execution gracefully skips.
  3. Execution Settlement & Cash Refund: Inside a transaction session:
    • The actual cost at the market execution price is computed: actualCost = qty * currentLTP.
    • Because currentLTP <= limitPrice, the actual cost is typically less than or equal to the reserved cash!
    • The leftover savings are returned directly to the user's available balance: 
      const refundAmount = order.reservedAmount - actualCost;
Funds.updateOne({ userId }, {
  $inc: {
    reservedBalance: -order.reservedAmount,
    usedBalance: +actualCost,
    availableBalance: +refundAmount // Leftover savings returned!
  }
});
    • Holding is credited with shares: quantity += qty.
    • Order is updated to status: 'completed', reservationReleased: true.
  4. User Cancellation (cancelLimitOrderService.js): If the trader cancels a pending limit order before it triggers:
    • Verifies order is in status: 'pending' and reservationReleased: false.
    • Atomically unlocks the reserved cash or reserved shares back to available status.
    • Marks order status: 'cancelled', reservationReleased: true.

8.1 The Three-Tier Balance Model

8.2 Fund Balance Invariants & Math Equations

The system enforces strict invariants on every transaction:

  1. Non-Negativity Constraint: availableBalance >= 0 and reservedBalance >= 0 at all times. Database schema enforces min: 0.
  2. Limit Order Placement Invariant:

    availableBalance_new = availableBalance_old - (qty * limitPrice)

    reservedBalance_new = reservedBalance_old + (qty * limitPrice)

  3. Limit Order Execution Invariant:

    reservedBalance_new = reservedBalance_old - reservedAmount

    usedBalance_new = usedBalance_old + (qty * LTP)

    availableBalance_new = availableBalance_old + (reservedAmount - (qty * LTP))

  4. Sell Holding Fulfillment Invariant:

    usedBalance_new = usedBalance_old - (qty * averagePurchasePrice)

    availableBalance_new = availableBalance_old + (qty * executionPrice)

    (Net Realized Profit/Loss immediately reflects in the increase/decrease of available cash!)

8.3 Deposits, Withdrawals & Transaction Ledger

All capital deposits and withdrawals are managed via backend/controller/fundController.js:

  • Adding Funds (POST /api/funds/add):

    Traders deposit virtual capital (e.g. ₹50,000 via simulated UPI or Netbanking). The transaction atomically increments availableBalance and creates a record in FundTransactionModel with type: 'deposit', status: 'completed'.

  • Withdrawing Funds (POST /api/funds/withdraw):

    Traders withdraw capital back to their bank account. The system validates that amount <= availableBalance. Funds deployed in active stocks (usedBalance) or reserved in open limit orders (reservedBalance) cannot be withdrawn until sold or canceled.

8.4 Transaction Helper: Atomic MongoDB Sessions

To guarantee complete ACID compliance without partial state corruption, database operations that span multiple collections (e.g. debiting funds and creating holdings) utilize backend/helpers/transactionHelper.js: 

export const runTransaction = async (callback) => {
  const session = await mongoose.startSession();
  session.startTransaction();
  try {
    const result = await callback(session);
    await session.commitTransaction();
    return result;
  } catch (error) {
    await session.abortTransaction();
    throw error;
  } finally {
    session.endSession();
  }
};

If any step inside callback throws an error (e.g., duplicate key, network blip, or constraint violation), the entire sequence aborts, rolling back any partial modifications to funds, orders, or holdings.

9.2 Volume-Weighted Average Purchase Price Formula

When a trader purchases additional shares of an already owned stock at a different market price, the new cost basis is calculated using the Volume-Weighted Average Price formula: 

New Average Price = ( (Existing Qty * Existing Avg Price) + (New Qty * Purchase Price) ) / ( Existing Qty + New Qty )

Worked Example:

  • Trader currently owns 10 shares of TCS with an average cost of ₹3,200 (Invested = ₹32,000).
  • Trader buys 5 additional shares of TCS at the current market price of ₹3,500 (New Outlay = ₹17,500).

New Total Quantity = 10 + 5 = 15 shares

New Total Invested = ₹32,000 + ₹17,500 = ₹49,500

New Average Price = ₹49,500 / 15 = ₹3,300 per share

9.3 Real-Time P&L Equations

The frontend Kite dashboard dynamically calculates real-time profit and loss metrics across every holding and for the aggregate portfolio:

1. Individual Holding Total P&L

Holding Invested Value = Quantity * Average Price
Holding Current Value  = Quantity * Current Market Price (LTP)
Total Profit / Loss    = Holding Current Value - Holding Invested Value
Percentage Return (%)  = ( Total Profit / Loss / Holding Invested Value ) * 100

2. Individual Holding Day P&L

Measures the profit or loss generated exclusively within the current trading session: 

Day Profit / Loss   = Quantity * ( Current Market Price - Previous Day Close Price )
Day Return (%)      = ( ( Current Market Price - Previous Close ) / Previous Close ) * 100

3. Portfolio Aggregate Metrics (PortfolioSummary.jsx)

  • Total Portfolio Invested = Sum of all (Quantity * Average Price)
  • Total Portfolio Current = Sum of all (Quantity * LTP)
  • Net Unrealized P&L = Total Portfolio Current - Total Portfolio Invested
  • Net Day P&L = Sum of all (Quantity * (LTP - Previous Close))

9.4 Sell Inventory Reservation (Anti-Double-Spend)

To prevent traders from placing multiple sell orders exceeding their actual owned shares:

  1. When a trader places a Limit Sell for 4 shares out of 10 owned shares: 
    Holding.updateOne({ userId, symbol }, {
  $inc: { quantity: -4, reservedQuantity: +4 }
});
  2. The available quantity immediately drops to 6 shares. If the user attempts to place another sell order for 7 shares, the system validates against quantity (6) and rejects the request.
  3. When the limit order executes, reservedQuantity is decremented by 4.
  4. If the user cancels the order, quantity is incremented by 4 and reservedQuantity is decremented by 4.

14.3 Concurrency Control & Race Condition Mitigation

High-frequency financial applications face severe concurrency vulnerabilities if state mutations are not carefully sequenced. Zerodha Clone implements multiple defense-in-depth mechanisms:

1. Anti-Double-Spend with Two-Phase Limit Order Locking

Vulnerability: If two TrueData market ticks arrive within 2 milliseconds of each other while an order is pending, two concurrent worker threads might both trigger execution for the same order, purchasing double the intended shares and causing balance corruption.

Mitigation: checkPendingLimitOrders.js uses an atomic atomic state transition from 'pending' to 'processing': 

const lockedOrder = await Order.findOneAndUpdate(
  { _id: order._id, status: 'pending' },
  { $set: { status: 'processing' } },
  { new: true }
);
if (!lockedOrder) return; // Second thread skipped immediately!

2. Exactly-Once Reservation Release Guard

Every order includes a boolean flag: reservationReleased: Boolean (default: false). When cash or stock is returned or converted to used margin: 

const order = await Order.findOneAndUpdate(
  { _id: orderId, reservationReleased: false },
  { $set: { reservationReleased: true, status: 'cancelled' } },
  { session }
);
if (!order) throw new Error("Reservation already released or order settled.");

This guarantees that user refunds can never be processed twice, even if multiple cancellation clicks occur in rapid succession.

3. Multi-Document ACID Transactions

All operations updating both ledger balances and asset inventories run inside native MongoDB replica-set transactions. If an order insertion fails after balance debiting, the entire transaction rolls back cleanly, ensuring zero financial discrepancy.

14.4 Error Handling Architecture

  • Centralized Error Class (AppError.js): Differentiates operational errors (known client errors like invalid inputs or insufficient margin) from fatal programmer bugs.
  • Fail-Fast DB Resilience: Mongoose is configured with bufferCommands: false. If the database connection drops, operations fail fast with meaningful error responses rather than hanging for 30-second timeouts.
  • Graceful Degradation: If external APIs (Twilio SMS or TrueData feeds) encounter downtime, fallbacks allow core application navigation and mock testing to proceed without crashes.

Part V: Trading Mechanics, Order Execution & Math (Questions 61–75)

61. What is the difference between a Market Order and a Limit Order?
A Market Order executes immediately at the current market LTP. A Limit Order executes only when market price reaches or improves upon a specified limit trigger price.
62. Walk through the cash reservation lifecycle of a Limit Buy order.
1) Placement: `availableBalance -= qty * limitPrice`, `reservedBalance += qty * limitPrice`. 2) Trigger: Executed at LTP. `reservedBalance -= reservedAmount`, `usedBalance += qty * LTP`. 3) Savings Refund: Leftover `(limitPrice - LTP) * qty` returns to `availableBalance`.
63. How is stock reserved on a Limit Sell order?
The shares are transferred from unencumbered `quantity` to `reservedQuantity` inside `Holding`. This prevents the trader from selling those same shares in a separate market order while the limit order is active.
64. What is the mathematical formula for Volume-Weighted Average Purchase Price?
`((Existing_Qty * Existing_Avg_Price) + (New_Qty * New_Price)) / (Existing_Qty + New_Qty)`.
65. If a user owns 20 shares of Reliance at ₹2,400 and buys 10 more at ₹2,700, what is the new average price?
Total Invested = (20 * 2400) + (10 * 2700) = 48,000 + 27,000 = ₹75,000. Total Shares = 30. New Average Price = 75,000 / 30 = ₹2,500 per share.
66. How does the system prevent double execution of a limit order when multiple ticks arrive?
Using two-phase atomic locking: the background worker queries for `status: 'pending'` and immediately transitions it to `'processing'`. A concurrent tick finding no order with status `'pending'` simply skips execution.
67. What is `reservationReleased` and why is it essential?
It is a boolean latch on the Order model. It ensures that unlocking reserved cash or shares occurs strictly once, preventing double refunds on duplicate cancellation clicks.
68. How is Day P&L calculated for an individual stock?
`Day P&L = Quantity * (Current Market Price - Previous Day Close Price)`.
69. How is Total Unrealized P&L calculated for a holding?
`Total P&L = Quantity * (Current Market Price - Average Purchase Price)`. Percentage return is `(Total P&L / (Quantity * Average Purchase Price)) * 100`.
70. What happens when a user cancels a pending Limit Buy order?
`cancelLimitOrderService.js` confirms status is `pending`, marks `reservationReleased: true`, decrements `reservedBalance` by `reservedAmount`, and increments `availableBalance` by `reservedAmount`.
71. Can a user withdraw funds that are currently in `reservedBalance`?
No. The withdrawal endpoint strictly checks `withdrawalAmount <= availableBalance`. Reserved funds are legally encumbered by pending market commitments.
72. How is intraday leverage modeled for MIS orders?
For MIS trades, required margin is computed as `(qty * price) / leverageFactor` (e.g. 5x leverage requires only 20% upfront cash), allowing intraday day-trading simulation.
73. What is short selling in MIS and how does the engine handle it?
A trader sells shares they do not own, creating a Position with `type: 'sell'`. They profit if price drops and must buy back (square-off) the shares before market close.
74. How does the engine handle orders placed when market prices fluctuate wildly (slippage)?
Market orders execute at the latest cached LTP. In a live production exchange, orders would route to an exchange matching engine with price tolerance bands.
75. What validation rules are applied to order placement payloads?
`orderValidation.js` enforces: `symbol` must be valid string, `qty` must be positive integer >= 1, `price` must be positive number >= 0.05, `mode` must be 'BUY' or 'SELL', `orderType` must be 'MARKET' or 'LIMIT'.
