Chapter 5 — Authentication, OTP & Security Architecture

5.1 Authentication Architecture Overview

Authentication is architected as a hybrid password and phone-based OTP system designed to mirror the multi-factor security expectations of modern Indian financial brokerages. The system uses signed JSON Web Tokens (JWT) transmitted via secure, HTTP-only cookies, paired with an active database-backed tokenVersion check that supports instant global session invalidation.

5.2 Mobile OTP Verification Challenge Flow

To prevent phone number spoofing and unauthorized account creation, mobile onboarding uses a multi-step challenge verification flow:

  1. Challenge Creation (POST /api/auth/otp/send):
    • User submits a 10-digit mobile number.
    • System validates number using regex /^\d{10}$/.
    • Rate-limiting check: Queries OtpChallengeModel to ensure no more than 3 challenges were requested in the last 5 minutes. If exceeded, returns HTTP 429.
    • Existing unconsumed challenges for this number are invalidated (isConsumed: true).
    • Dispatches verification SMS via Twilio Verify. If Twilio credentials are not configured, the system logs a mock challenge code (123456) to ensure uninterrupted development and testing.
  2. Challenge Verification (POST /api/auth/register/verify-mobile):
    • User submits the 6-digit OTP code received on SMS.
    • Twilio Verify checks code validity (or verifies against test mock code 123456).
    • Upon approval, the challenge is marked isConsumed: true.
    • A short-lived signed JWT verification token is generated: jwt.sign({ mobile, verified: true, challengeId }, JWT_SECRET, { expiresIn: '15m' }).
    • This token must be included in the subsequent registration payload to prove phone ownership.

5.3 User Registration & Client ID Generation

Once verified, the user submits registration details (POST /api/auth/register):

  • Validates name, unique email, verified mobile, password (minimum 6 characters), and verificationToken.
  • Decodes the verification token, confirms that decoded.mobile === req.body.mobile and decoded.verified === true.
  • Validates that the challenge record has not already been used for registration (challenge.usedForRegistration === false), then marks it used.
  • Generates a unique Zerodha 6-character Client ID (e.g., ZR9669) using random alphanumeric character generation and collision detection.
  • Hashes the password with bcryptjs using 10 salt rounds.
  • Initializes a default Funds document for the new user with ₹1,00,000 initial virtual capital.
  • Initializes a default WatchlistList titled "Watchlist 1" populated with blue-chip Indian equities (Reliance, TCS, Infosys, HDFC Bank, ICICI Bank, SBI, ITC, Bharti Airtel).
  • Signs the session JWT and sets the HTTP-only cookie, automatically logging the user into their account.

5.4 Token Versioning & Global Session Revocation

A frequent security flaw in stateless JWT architectures is the inability to revoke tokens before their expiration window elapses. Zerodha Clone solves this using Token Versioning: 

// JWT Payload structure:
{
  "userId": "68c123456789abcdef123455",
  "role": "trader",
  "tokenVersion": 3,
  "iat": 1791780813,
  "exp": 1792385613
}

When a user invokes POST /api/auth/logout-other-sessions or changes their password:

  1. The backend executes User.findByIdAndUpdate(userId, { $inc: { tokenVersion: 1 } }).
  2. The current active user is re-issued a fresh cookie with the incremented version.
  3. Every subsequent request from any other device or browser containing the older tokenVersion fails the check in isLoggedInMiddleware.js: 
    if (user.tokenVersion !== decoded.tokenVersion) {
  return res.status(401).json({
    success: false,
    message: "Session expired. Please login again."
  });
}
  4. All previous sessions are immediately invalidated across all devices without requiring a centralized token blacklist.

5.5 Cookie Security Specifications

Cookie Attribute Configuration Security Protection Provided
httpOnly true Prevents client-side JavaScript from accessing document.cookie, completely mitigating Cross-Site Scripting (XSS) token theft.
sameSite 'lax' Protects against Cross-Site Request Forgery (CSRF) by preventing third-party origins from sending the authentication cookie during cross-site requests.
maxAge 24 * 60 * 60 * 1000 (1 day) Enforces session lifecycle boundaries, ensuring stale sessions expire naturally.
secure Conditional (false in dev, true in HTTPS prod) Ensures authentication cookies are transmitted exclusively over encrypted TLS connections in production.
