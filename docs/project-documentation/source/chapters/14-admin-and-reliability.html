Chapter 14 — Admin Operations, Concurrency & Reliability

14.1 Role-Based Access Control (RBAC) & Admin Middleware

Administrative capabilities are strictly guarded using role-based access control. The UserModel defines a role enum ('trader' | 'admin'). Sensitive endpoints, such as tournament creation, manual square-offs, and platform settings, are protected by adminMiddleware.js: 

export const adminOnly = (req, res, next) => {
  if (!req.user || req.user.role !== "admin") {
    return res.status(403).json({
      success: false,
      message: "Forbidden: Administrative privileges required."
    });
  }
  next();
};

The system includes administrative utility scripts (backend/scripts/setAdminRole.js) allowing system operators to safely grant administrative permissions by email address.

14.2 Tournament Administration Interface (TournamentAdmin.jsx)

Administrators access a dedicated management portal (/admin/tournaments) providing:

  • Tournament Creation Form: Configuring title, description, entry fee, initial virtual balance (e.g. ₹5,00,000), registration window, competition start date/time, and end date/time.
  • Competition Lifecycle Controls: Ability to view enrolled participants, inspect aggregate virtual portfolios, and manually trigger emergency freezes or lifecycle status transitions.
  • Audit Trails (adminAudit.js): Every administrative mutation logs the executing administrator's ID, action timestamp, IP address, and changed parameters for compliance and debugging.

14.3 Concurrency Control & Race Condition Mitigation

High-frequency financial applications face severe concurrency vulnerabilities if state mutations are not carefully sequenced. Zerodha Clone implements multiple defense-in-depth mechanisms:

1. Anti-Double-Spend with Two-Phase Limit Order Locking

Vulnerability: If two TrueData market ticks arrive within 2 milliseconds of each other while an order is pending, two concurrent worker threads might both trigger execution for the same order, purchasing double the intended shares and causing balance corruption.

Mitigation: checkPendingLimitOrders.js uses an atomic atomic state transition from 'pending' to 'processing': 

const lockedOrder = await Order.findOneAndUpdate(
  { _id: order._id, status: 'pending' },
  { $set: { status: 'processing' } },
  { new: true }
);
if (!lockedOrder) return; // Second thread skipped immediately!

2. Exactly-Once Reservation Release Guard

Every order includes a boolean flag: reservationReleased: Boolean (default: false). When cash or stock is returned or converted to used margin: 

const order = await Order.findOneAndUpdate(
  { _id: orderId, reservationReleased: false },
  { $set: { reservationReleased: true, status: 'cancelled' } },
  { session }
);
if (!order) throw new Error("Reservation already released or order settled.");

This guarantees that user refunds can never be processed twice, even if multiple cancellation clicks occur in rapid succession.

3. Multi-Document ACID Transactions

All operations updating both ledger balances and asset inventories run inside native MongoDB replica-set transactions. If an order insertion fails after balance debiting, the entire transaction rolls back cleanly, ensuring zero financial discrepancy.

14.4 Error Handling Architecture

  • Centralized Error Class (AppError.js): Differentiates operational errors (known client errors like invalid inputs or insufficient margin) from fatal programmer bugs.
  • Fail-Fast DB Resilience: Mongoose is configured with bufferCommands: false. If the database connection drops, operations fail fast with meaningful error responses rather than hanging for 30-second timeouts.
  • Graceful Degradation: If external APIs (Twilio SMS or TrueData feeds) encounter downtime, fallbacks allow core application navigation and mock testing to proceed without crashes.
