Chapter 8 — Funds Management & Ledger Architecture

8.1 The Three-Tier Balance Model

Standard e-commerce architectures store a single monolithic wallet balance (e.g. wallet = 500). In financial trading systems, a single balance is inadequate because active holdings, margin exposure, and unfilled limit orders require separate capital allocations. Zerodha Clone implements an institutional three-tier balance ledger: 

┌────────────────────────────────────────────────────────────────────────┐
│                        Total Account Equity                            │
│  (Total Account Value = Available Cash + Used Margin + Portfolio Value)│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
          ┌─────────────────────────┼─────────────────────────┐
          ▼                         ▼                         ▼
  availableBalance             usedBalance             reservedBalance
  ┌───────────────┐         ┌───────────────┐         ┌───────────────┐
  │ Free cash     │         │ Capital tied  │         │ Cash locked   │
  │ available for │         │ up in active  │         │ for pending   │
  │ new orders    │         │ stock holding │         │ buy limit     │
  │ or withdrawal │         │ cost basis    │         │ orders        │
  └───────────────┘         └───────────────┘         └───────────────┘

8.2 Fund Balance Invariants & Math Equations

The system enforces strict invariants on every transaction:

  1. Non-Negativity Constraint: availableBalance >= 0 and reservedBalance >= 0 at all times. Database schema enforces min: 0.
  2. Limit Order Placement Invariant:

    availableBalance_new = availableBalance_old - (qty * limitPrice)

    reservedBalance_new = reservedBalance_old + (qty * limitPrice)

  3. Limit Order Execution Invariant:

    reservedBalance_new = reservedBalance_old - reservedAmount

    usedBalance_new = usedBalance_old + (qty * LTP)

    availableBalance_new = availableBalance_old + (reservedAmount - (qty * LTP))

  4. Sell Holding Fulfillment Invariant:

    usedBalance_new = usedBalance_old - (qty * averagePurchasePrice)

    availableBalance_new = availableBalance_old + (qty * executionPrice)

    (Net Realized Profit/Loss immediately reflects in the increase/decrease of available cash!)

8.3 Deposits, Withdrawals & Transaction Ledger

All capital deposits and withdrawals are managed via backend/controller/fundController.js:

  • Adding Funds (POST /api/funds/add):

    Traders deposit virtual capital (e.g. ₹50,000 via simulated UPI or Netbanking). The transaction atomically increments availableBalance and creates a record in FundTransactionModel with type: 'deposit', status: 'completed'.

  • Withdrawing Funds (POST /api/funds/withdraw):

    Traders withdraw capital back to their bank account. The system validates that amount <= availableBalance. Funds deployed in active stocks (usedBalance) or reserved in open limit orders (reservedBalance) cannot be withdrawn until sold or canceled.

8.4 Transaction Helper: Atomic MongoDB Sessions

To guarantee complete ACID compliance without partial state corruption, database operations that span multiple collections (e.g. debiting funds and creating holdings) utilize backend/helpers/transactionHelper.js: 

export const runTransaction = async (callback) => {
  const session = await mongoose.startSession();
  session.startTransaction();
  try {
    const result = await callback(session);
    await session.commitTransaction();
    return result;
  } catch (error) {
    await session.abortTransaction();
    throw error;
  } finally {
    session.endSession();
  }
};

If any step inside callback throws an error (e.g., duplicate key, network blip, or constraint violation), the entire sequence aborts, rolling back any partial modifications to funds, orders, or holdings.
