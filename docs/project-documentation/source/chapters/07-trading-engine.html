Chapter 7 — Trading Engine & Order Execution

7.1 Trading Engine Architecture Overview

The core of the platform is an institutional paper-trading engine that faithfully replicates the financial rules, balance management, and lifecycle state transitions of real-world stock exchanges. It enforces atomic transaction safety, prevents overdrafts, implements cash and inventory reservations, and matches limit orders in real time against live market ticks.

7.2 Market Order Execution (Immediate Fill)

When a trader submits a Market Order:

  1. Price Resolution: The engine resolves the latest market price (LTP) from the in-memory cache populated by TrueData feeds.
  2. Pre-Trade Validation:
    • BUY Market: The total required capital is calculated: tradeAmount = qty * LTP. The system queries Funds inside an atomic MongoDB session. If availableBalance < tradeAmount, the transaction aborts with an Insufficient Funds error.
    • SELL Market (CNC): The system queries Holding for the user and symbol. If holding.quantity < qty, the transaction aborts with an Insufficient Quantity error. Short selling is prohibited in CNC delivery.
  3. Atomic Ledger & Inventory Mutation: Inside a MongoDB transaction session:
    • BUY CNC: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: -tradeAmount, usedBalance: tradeAmount }
});
Holding.findOneAndUpdate({ userId, symbol }, {
  $inc: { quantity: qty },
  $set: { averagePrice: newWeightedAverage, currentPrice: LTP }
}, { upsert: true });
    • SELL CNC: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: +tradeAmount, usedBalance: -originalCostBasis }
});
Holding.updateOne({ userId, symbol }, {
  $inc: { quantity: -qty }
});
      If the remaining holding quantity reaches 0, the holding document is removed.
  4. Order Insertion: An order document is created with status: 'completed', orderType: 'MARKET', and reservationReleased: true.

7.3 Limit Order Lifecycle & Reservation Engine

A Limit Order allows a trader to specify an exact maximum price they are willing to pay (Limit Buy) or minimum price they are willing to accept (Limit Sell). Because execution may occur minutes or hours later, the engine locks capital or inventory to guarantee settlement when the market condition triggers.

Step-by-Step Limit Order Lifecycle:

  1. Placement & Reservation (createOrderServices.js):
    • Limit BUY: The maximum required cash is calculated: reservedAmount = qty * limitPrice. This amount is moved immediately from availableBalance to reservedBalance: 
      Funds.updateOne({ userId }, {
  $inc: { availableBalance: -reservedAmount, reservedBalance: +reservedAmount }
});
      The order is recorded with status: 'pending', reservedAmount, and reservationReleased: false.
    • Limit SELL: The share quantity is reserved from the holding: 
      Holding.updateOne({ userId, symbol }, {
  $inc: { quantity: -qty, reservedQuantity: +qty }
});
  2. Background Tick Evaluation (checkPendingLimitOrders.js): Whenever TrueData streams a price update (e.g., RELIANCE LTP = ₹2,480):
    • The worker queries for active pending orders for that symbol: Order.find({ symbol, status: 'pending' }).
    • Condition Check:
      • BUY Limit: Triggers if currentLTP <= order.price.
      • SELL Limit: Triggers if currentLTP >= order.price.
    • Two-Phase Execution Lock: To prevent race conditions from concurrent ticks, the worker uses an atomic lock: 
      const lockedOrder = await Order.findOneAndUpdate(
  { _id: order._id, status: 'pending' },
  { $set: { status: 'processing' } },
  { new: true }
);
      If another thread already acquired the lock, lockedOrder is null and execution gracefully skips.
  3. Execution Settlement & Cash Refund: Inside a transaction session:
    • The actual cost at the market execution price is computed: actualCost = qty * currentLTP.
    • Because currentLTP <= limitPrice, the actual cost is typically less than or equal to the reserved cash!
    • The leftover savings are returned directly to the user's available balance: 
      const refundAmount = order.reservedAmount - actualCost;
Funds.updateOne({ userId }, {
  $inc: {
    reservedBalance: -order.reservedAmount,
    usedBalance: +actualCost,
    availableBalance: +refundAmount // Leftover savings returned!
  }
});
    • Holding is credited with shares: quantity += qty.
    • Order is updated to status: 'completed', reservationReleased: true.
  4. User Cancellation (cancelLimitOrderService.js): If the trader cancels a pending limit order before it triggers:
    • Verifies order is in status: 'pending' and reservationReleased: false.
    • Atomically unlocks the reserved cash or reserved shares back to available status.
    • Marks order status: 'cancelled', reservationReleased: true.

7.4 Mathematical Worked Example: Limit Buy Execution

Scenario:
  • User has ₹1,00,000 available balance.
  • Places a Limit Buy for 10 shares of Reliance at Limit Price ₹2,500.
  • Market dips to ₹2,480, triggering execution.
Step 1: Placement
  • reservedAmount = 10 * ₹2,500 = ₹25,000
  • availableBalance = ₹1,00,000 - ₹25,000 = ₹75,000
  • reservedBalance = ₹25,000
  • usedBalance = ₹0
Step 2: Execution at ₹2,480
  • actualCost = 10 * ₹2,480 = ₹24,800
  • refundAmount = ₹25,000 - ₹24,800 = ₹200
  • reservedBalance = ₹25,000 - ₹25,000 = ₹0
  • usedBalance = ₹0 + ₹24,800 = ₹24,800
  • availableBalance = ₹75,000 + ₹200 = ₹75,200
  • Total Account Equity = ₹75,200 (cash) + ₹24,800 (stock value) = ₹1,00,000
